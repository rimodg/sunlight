# The roster

Written November 24, 2026. Build step 5, second part: which watchers exist,
each with its seal, as one hashed list that the measure scripts and the
verifiers read from. A watcher not on the roster does not run.

## What the roster is

`config/roster.json` (schema `sunlight.roster.v1`) is a list of the watchers
that may run. Each entry names one watcher file under `config/watchers/` and
pins what `code/watcher.py` seals from it:

- `watcher_id` and `rule_id`, as the watcher file and its rule declare them.
- `watcher_sha256`: the SHA-256 of the watcher file bytes.
- `rule_version_sha256`: the rule version from `code/custody.py` (rule
  module bytes, profile bytes, every source the profile cites).
- `watcher_seal_sha256`: the watcher's seal (the above plus every source
  the facts cite).

Entries are ordered by `watcher_id`, ids and files are distinct, and
`roster_sha256` is the SHA-256 over everything else in the file. A changed
byte of any watcher file, any rule module, any profile or any cited source
changes a seal, and a changed seal changes the roster hash.

`code/roster.py` reads the roster part by part and refuses any missing,
malformed or extra part, an unordered or duplicated list, a file outside
`config/watchers/`, or a `roster_sha256` that does not recompute. It infers,
scores and judges nothing: a mismatch is refused, never repaired. Missing is
not zero: a watcher without a roster entry has no standing, and nothing
supplies one.

## How a watcher runs

Both measure scripts (`scripts/measure_events_in_order.py`,
`scripts/measure_section53.py`) now load the roster before they read a
record. `roster.enrol` finds the entry for the watcher file and compares it
with the seal recomputed from the checkout: id, file hash, rule id, rule
version and seal. Any difference, or no entry, raises before any row is read.
The rule did not run, and the script says why.

Each results file (`sunlight.events-in-order-results.v4`,
`sunlight.section53-results.v4`) carries a file-level `roster` block: the
roster file path, the SHA-256 of its bytes, `roster_sha256` and the number of
watchers on it. Rows are unchanged: every row of both files, custody stamp and
`result_sha256` included, is byte for byte what the schema v3 files carried
(`tests/test_roster.py` pins the digest of both row lists).

## How to verify

From a checkout, reads only:

    PYTHONPATH=code python scripts/verify_roster.py \
      research/events_in_order_2026-11-18/results.json \
      research/section53_2026-11-13/adapter-run/results.json

This loads the roster, seals every watcher it names from the checkout and
compares each entry part by part, reports any file under `config/watchers/`
the roster does not name, and for each results file checks that it names
this roster (by bytes and by content) and that the watcher whose seal it
carries is on the roster with that seal. Exit 0 means every link holds.

To record a new roster after a watcher, rule or profile changes:

    PYTHONPATH=code python scripts/seal_roster.py > config/roster.json

`seal_roster.py` prints and writes nothing itself. The new roster is committed
with the change it answers to, and the results files are replayed so they
name it. The watcher verifier, the custody verifiers and
`scripts/verify_section53_evidence.py` are unchanged and still exit 0.
